# Specification: AI System (`ai_manager.spec.md`)

**Version:** 2.0
**Date:** 2025-04-16

## 1. Introduction

The AI System is responsible for controlling the behavior of non-player character (NPC) units (Enemy and Allied AI) during their respective phases. It determines the actions each AI-controlled unit will take based on their assigned AI profile, the current game state, map layout, and objectives.

This specification outlines a **modular architecture** designed for flexibility, testability, and extensibility. The core responsibilities are distributed among several key components:

*   **AI Turn Processor:** Orchestrates the AI phase, iterating through units and coordinating the decision-making process.
*   **AI Profile Manager:** Loads, caches, and provides access to `AIProfile` data for units.
*   **AI Action Evaluator:** Generates a list of all possible valid actions (movement, attacks, captures, item use, etc.) a unit can perform given the current game state.
*   **AI Action Scoring:** Calculates a utility score for each potential action based on the unit's AI profile, archetype logic, and the tactical situation.
*   **Archetype Handlers:** Encapsulate the specific decision-making logic and scoring adjustments for different AI behaviors (e.g., `ChargeHandler`, `HealSupportHandler`, `ThiefLootHandler`).

This modular approach replaces the previous monolithic `AIManager`, allowing for easier modification and addition of new AI behaviors.

## 2. Dependencies

The AI System components collectively require access to and interaction with:

*   **Game State Manager:** To query the current game state (unit positions, stats, inventory, turn, factions, objectives).
*   **Unit System:** To get detailed unit information (stats, class, skills, inventory, status, AI profile key).
*   **Map System:** To understand map layout, terrain, movement costs, line of sight, objectives, interactable objects (chests, doors).
*   **Movement System:** To calculate valid movement ranges and paths.
*   **Combat System:** To predict combat outcomes for evaluating potential attacks/captures.
*   **Action Handler:** To execute the final chosen action sequence.
*   **Data Provider:** To access AI profile definitions (likely from YAML/JSON files).
*   **Other Gameplay Systems:** As needed for specific actions (e.g., `CaptureSystem`, `StealingSystem`, `StaffSystem`, `MapInteractionSystem`).

## 3. Data Structures

### 3.1. `AIProfile`

Defines the behavioral parameters for an AI unit. Managed by the `AIProfileManager`.

```
AIProfile {
    profile_id: String // Unique identifier (e.g., "Generic_Charge", "Boss_Guard_Throne")
    behavior_archetype: Enum(CHARGE, GUARD, DEFEND_AREA, ESCAPE, HEAL_SUPPORT, CAPTURE_PRIORITY, THIEF_LOOT, BOSS_GUARD, FOLLOW_PLAYER, OBJECTIVE_ORIENTED) // Primary behavior mode, determines which ArchetypeHandler is used.
    aggression_level: Float // (0.0 to 1.0) Influences risk-taking in scoring.
    target_preference: Enum(NEAREST, WEAKEST, HIGHEST_DAMAGE, HIGHEST_THREAT, CAPTURABLE, SPECIFIC_UNIT_TYPE) // Default target prioritization.
    movement_target: Coordinate or UnitID or None // Specific destination or unit focus.
    guard_radius: Integer or None // For GUARD/DEFEND_AREA: pursuit range.
    heal_threshold_ally: Float // HP% threshold for allied healing.
    heal_threshold_self: Float // HP% threshold for self-healing.
    retreat_threshold: Float // HP% threshold to consider retreat behaviors.
    capture_enabled: Boolean // Can this unit capture?
    use_status_staves: Boolean // Will this unit use offensive staves?
    special_flags: List[String] // e.g., ["IGNORE_LOW_HIT_CHANCE", "PRIORITIZE_FLYERS", "TRADE_CAPTURED_ITEMS"] // For fine-tuning behavior.
}
```

### 3.2. `AIAction`

Represents a potential action sequence evaluated by the system. Generated by `AIActionEvaluator`, scored by `AIActionScoring`.

```
AIAction {
    unit_id: UnitID
    action_type: Enum(MOVE, ATTACK, CAPTURE, USE_ITEM, USE_STAFF, WAIT, TRADE, ESCAPE, VISIT, TALK, INTERACT_MAP, STEAL)
    move_target_coord: Coordinate // Destination tile for movement (can be same as current position)
    action_target: Coordinate or UnitID or ItemID // Target of the action (enemy, ally, item, tile)
    predicted_utility: Float // Score assigned by AIActionScoring + ArchetypeHandler
    path: List[Coordinate] // The path taken (if action_type involves movement)
    // Optional context added during generation/scoring
    context: Dict // e.g., {"combat_prediction": {...}, "item_to_steal": ItemID}
}
```

## 4. Functional Requirements

### 4.1. Turn Processing (AI Turn Processor)

*   **FR-AI-001:** The `AITurnProcessor` shall iterate through all active units belonging to the current AI faction at the start of their phase.
*   **FR-AI-002:** For each active AI unit, the `AITurnProcessor` shall coordinate with other AI components to determine and execute the best possible action sequence.
*   **FR-AI-003:** The order of AI unit processing shall be deterministic.

### 4.2. Profile Management (AI Profile Manager)

*   **FR-AI-004:** The `AIProfileManager` shall load `AIProfile` definitions from data sources.
*   **FR-AI-005:** The `AIProfileManager` shall provide the correct `AIProfile` for a given unit based on its assigned profile key (e.g., from unit data).

### 4.3. Action Generation (AI Action Evaluator)

*   **FR-AI-006:** For a given unit, the `AIActionEvaluator` shall generate a comprehensive list of all potential `AIAction` sequences available. This includes:
    *   Moving to all reachable tiles.
    *   Attacking reachable targets from the current position and potential move destinations.
    *   Capturing eligible targets.
    *   Using items (self).
    *   Using staves (allies/enemies).
    *   Waiting.
    *   Escaping (if applicable).
    *   Visiting/Talking (if applicable).
    *   Interacting with map objects (Chests, Doors).
    *   Stealing from adjacent targets.
    *   Trading with adjacent allies.
*   **FR-AI-007:** The `AIActionEvaluator` shall leverage other systems (`MovementSystem`, `CombatSystem`, `MapSystem`, etc.) to determine action validity and gather necessary context (e.g., combat predictions).

### 4.4. Action Scoring (AI Action Scoring & Archetype Handlers)

*   **FR-AI-008:** The `AIActionScoring` component shall calculate a base utility score for each generated `AIAction`. This base score considers generic factors like:
    *   Damage dealt/taken.
    *   Kill potential.
    *   Healing provided.
    *   Status effects applied/cured.
    *   Objective proximity/completion.
    *   Resource cost (item uses).
    *   Positional safety/advantage (terrain).
*   **FR-AI-009:** The `AITurnProcessor` (or `AIActionScoring`) shall select the appropriate `ArchetypeHandler` based on the unit's `AIProfile.behavior_archetype`.
*   **FR-AI-010:** The selected `ArchetypeHandler` shall adjust the base utility scores or apply specific filtering logic based on the archetype's goals and the `AIProfile` parameters (e.g., a `HealSupportHandler` drastically increases utility for healing actions; a `GuardHandler` filters out actions moving too far from the post).
*   **FR-AI-011:** Archetype Handlers implement the specific logic detailed in FR-AI-010 to FR-AI-019 of the previous spec version (Charge, Guard, Defend, Escape, Heal, Capture, Thief, Retreat, Status Staff, Trade).

### 4.5. Action Selection & Execution (AI Turn Processor)

*   **FR-AI-012:** The `AITurnProcessor` shall select the `AIAction` with the highest final `predicted_utility` score after archetype adjustments. Ties broken deterministically.
*   **FR-AI-013:** The `AITurnProcessor` shall pass the selected `AIAction` to the `Action Handler` for execution.

        sorted_units = sort_units_by_processing_order(ai_units)

            if unit.can_act():
                best_action = determine_unit_action(unit)
                if best_action:
                    action_handler.execute_action(best_action)
                else:
                    // Fallback: Wait if no other action is chosen

        // 1. Generate all possible actions
        potential_actions = action_evaluator.generate_actions(unit, game_state)
        // TDD_ANCHOR: Test Action Evaluator generates Move, Wait, Attack, etc.

        if not potential_actions:
            return create_wait_action(unit)

        action_scorer.score_actions(potential_actions, unit, profile, game_state)
        // TDD_ANCHOR: Test Action Scorer assigns base utility (e.g., damage dealt)

        // 3. Apply archetype-specific logic/scoring adjustments

        if archetype in archetype_handlers:

            final_actions = handler.refine_actions(potential_actions, unit, profile, game_state)

        else:
            final_actions = potential_actions // Default if no specific handler

        if not final_actions:

        // 4. Select the best action
        best_action = select_highest_utility_action(final_actions)

## 7. Open Questions / Future Considerations

*   Detailed formulas/heuristics for base utility scoring in `AIActionScoring`.
*   Implementation details of specific `ArchetypeHandler` logic.
*   Handling of coordinated AI tactics (multiple units).
*   Performance optimization for action generation/scoring on large maps/unit counts.
*   Refining NPC AI behaviors (Follow Player, Talk interactions).
*   Standardized way for systems like `StealingSystem` or `CaptureSystem` to provide necessary info for evaluation (e.g., `can_steal`, `predict_steal_chance`).
